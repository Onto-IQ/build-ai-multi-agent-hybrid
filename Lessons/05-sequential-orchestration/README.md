# Module 05 — สายการผลิตบน OpenCode

## Key idea / แนวคิดหลัก — เล่าเป็นเรื่อง

งานจริงไม่ใช่คำสั่งก้อนเดียวจบ แต่เป็นสายพาน: คนวางแผนออกใบสั่งงาน → คนทำทำทีละสาย → ของชิ้นก่อนต้องอยู่บนไฟล์ก่อนชิ้นถัดไปเริ่ม แล็บนี้ฝึกจังหวะนั้นบน OpenCode ด้วยบทบาท `planner` ที่เขียนได้ไฟล์เดียว (`docs/TASKS.md`) แล้วค่อยสั่งทำทีละสาย data → backend → frontend เหตุผลที่ต้องแยกสายคือ**เคสพังของแต่ละสายอยู่คนละไฟล์** ทำพร้อมกันเมื่อพังจะหายาก ทำทีละสายเมื่อพังรู้ทันทีว่าสายไหน

สิ่งที่ทำให้สายพานนี้วัดได้คือด่าน: จบโมดูลนี้ด่านต้องเขียว **2 ข้อพอดี** (`data-quality` และ `summary-matches-valid-rows`) ด้วยตัวเลข 16,772 กิจการ / ทุนรวม 45,341,868,784 บาท ส่วนโน้ตกับ health ยังต้องแดง เพราะงานนั้นเป็นของ Module 06 ถ้าผู้ช่วย "ใจดี" ช่วยปิดเคสโน้ตเองด้วย ให้ย้อน — ของล้วนของห้องคือยอมรับว่ายังไม่ครบ

## Concept / เนื้อหา

### Part A — สามสายและไฟล์ที่ถือ

| สาย | ไฟล์ที่ถือ | ผลงาน (จากเครื่องทดสอบจริง) |
|---|---|---|
| planner | `docs/TASKS.md` เท่านั้น | แผน 3 สายพร้อม CONSTRAINTS กันแก้ด่าน กันแตะโน้ต/health |
| data | `docs/DESIGN.md`, `scripts/clean-export.sql`, `data/dataset.csv` | SQL อ่าน parquet → กรองแถวขยะ 9 แถว → แปลง พ.ศ.−543 เป็น ISO → ดึงจังหวัดจากที่อยู่ → CSV สะอาด 16,772 แถวเป๊ะ |
| backend | `server.js` จุดเดียว (`/api/summary`) | ทิ้ง parser พัง (`split(',')` + `capital_raw`) ไปเรียก `analyze()` ตัวเดียวกับด่าน — diff สั้น แต่โครงเปลี่ยน |
| frontend | `web/` | โชว์ยอดจริงจาก `/api/summary` พร้อมเครดิต data.go.th |

### Part B — SQL วนแก้สามรอบ และความหมายของเฉลย

รอบทดสอบจริงโมเดลเขียน SQL พังสามรอบต่อเนื่อง (ชื่อคอลัมน์ผิด → ชนิดข้อมูลชนตอนลบ 543 ปี → ใช้ `REGEXP` เป็นตัวดำเนินการที่ DuckDB ไม่มี) สุดท้ายใช้ของอ้างอิงจาก `node scripts/catch-up.js w3` ผ่านทันที บทเรียนไม่ใช่ "โมเดลไม่เก่ง" แต่คือ **วงจรรัน-ส่ง error-แก้ มีค่าเมื่อใกล้จะโดน** และเฉลยมีไว้ให้ก้าวข้ามจุดคอขวด ไม่ใช่ให้ลอกตั้งแต่ต้น จุดที่ควรเรียนจาก SQL เฉลยคือสามเทคนิค: `strptime(...) - INTERVAL 543 YEAR` สำหรับ พ.ศ., `try_cast(... ) IS NOT NULL` กรองแถวขยะใน WHERE, และ `row_number() OVER (... ORDER BY strpos DESC)` เลือกจังหวัดที่ปรากฏใกล้ท้ายที่อยู่ที่สุด

### Part C — สองอุบัติเหตุที่โมดูลนี้สอนโดยไม่ได้ตั้งใจ

1. **ไฟล์กฎที่แชร์กับด่านคือดินระเบิด** — รอบทดสอบโมเดล refactor `parseRows` ใน `lib/inspect-data.js` (ไฟล์กฎที่ด่านเรียกใช้) โดยลืม import ทำให้ด่าน abort ทั้งตัว ก่อนรันด่านรอบสำคัญให้เช็ก `git status` ว่ามีไฟล์กฎถูกแก้หรือเปล่า ถ้ามีและไม่จำเป็น ให้ `git checkout -- lib/inspect-data.js`
2. **พอร์ตค้างจากการทดสอบของผู้ช่วย** — โมเดลรัน `npm start` ทิ้งไว้ ด่านรอบถัดไม FAIL ทั้งกลุ่มด้วย "port 3000 is already in use" ปิดก่อนรันด่านทุกครั้ง

## ลำดับในห้อง (ภาพรวม)

1. สร้าง `planner.md` → ตรวจ frontmatter ด้วยตา → ปิดเปิด opencode ใหม่
2. สั่ง planner เขียน `docs/TASKS.md` → ตรวจว่ามีสามสายครบ
3. สาย data → รัน `duckdb` เอง + `echo $LASTEXITCODE` → นับบรรทัด ~16,773 ดู 3 แถวแรกเป็น ISO
4. สาย backend → สาย frontend (ทีละสาย รอจบก่อนส่งอันถัดไป)
5. `npm start` ดูหน้าเว็บโชว์ 16,772 / 45,341,868,784 แล้ว `Ctrl+C` ปิดก่อนรันด่าน
6. `npm run gate` + `echo $LASTEXITCODE` → PASS 2 ข้อพอดี exit `2`
7. รอบรีวิว: สั่งเขียน `docs/REVIEW.md` เทียบ SQL กับ DESIGN — ห้ามแก้ของ

แบบฝึกหัดเต็มอยู่ที่ [LAB.md](LAB.md) ประมาณ 60 นาที ต้องมี DuckDB ก่อนเริ่ม

## Common pitfalls / กับดัก (จากเครื่องทดสอบจริง)

- **planner.md ไม่มี YAML frontmatter** — โมเดลเขียนเป็นหัวข้อ markdown ธรรมดา ต้องเติมบล็อก `---` เองตามขั้นตรวจด้วยตา
- **คลิปบอร์ดไทยเพี้ยน** — ตั้งคลิปบอร์ดผ่าน `Get-Content` โดยไม่ใส่ `-Encoding UTF8` แล้วข้อความไทยกลายเป็นตัวมัวทั้งก้อนถูกส่งไปเป็นคำสั่ง (เคสจริง: กลายเป็นเรื่อง A/B prefill ที่ไม่เกี่ยวกับงาน) ดูช่องพิมพ์ใน TUI ก่อนกด Enter เสมอ
- **Z.AI overload วน retry นานสุด ~12 นาทีต่อคำสั่งใหญ่** — ให้มันลองเอง อย่ากด Esc ถ้ายังเห็น "Retrying ... attempt N"
- **ผู้ช่วยสร้างไฟล์เกินสั่ง** — รอบทดสอบเกินมาเป็น DELIVERABLES/QUICK-START/SUMMARY/VERIFICATION.md ไฟล์ที่ไม่อยู่ในแผนให้ลบทิ้ง อย่าเผลอ commit
- **แก้ lib/inspect-data.js โดยไม่จำเป็น** — ดู Part C ข้อ 1
- **ห้ามลืมว่า backend ยังต้องพังเรื่อง JSON/health/โน้ต** — ถ้าผู้ช่วยแก้พาดพิงถึงสามจุดนี้ ให้ย้อน diff

## Quick check / ทบทวน

- ทำไม planner ต้องเขียนได้ไฟล์เดียว? — เพื่อให้แผนเป็นของที่ตรวจได้ก่อนแรงงานเริ่ม และกันคนวางแผนลงมือแก้โค้ดเอง
- ทำไมสาย backend ถึงจบด้วย diff สั้น? — เพราะทางที่ถูกคือลบ logic สองอย่างที่ทำซ้ำ (parse + นับ) ไปเรียก `analyze()` ตัวเดียวกับด่าน ไม่ใช่เขียนการคำนวณใหม่ให้ตรงเอง
- ด่านควรจบกี่ข้อเขียว ตอนจบโมดูลนี้? — สองข้อพอดี (ข้อมูล + ยอดสรุป) ที่เหลือแดงคือของ Module 06 ถ้าเขียวเกินแปลว่ามีคน "ช่วย" เกินขอบเขต
- ทำไมต้องมี `docs/REVIEW.md` ทั้งที่ด่านผ่านแล้ว? — เพราะด่านวัดผลสุดท้าย แต่รีวิววัดว่า SQL ตรงกับสัญญาที่ DESIGN ประกาศไว้ไหม จุดต่างที่ด่านยังไม่จับคือของที่ไล่บั๊กใน Module 06 ต้องอ่าน

## Go deeper

- เปิด `docs/TASKS.md` เทียบกับงานจริงที่ทำ ดูว่าแผนกับของจริงต่างกันตรงไหน และเพราะอะไร
- อ่าน SQL ใน `scripts/clean-export.sql` ทีละ CTE แล้วอธิบายได้ว่าทำไมต้อง `row_number()` ตอนเลือกจังหวัด
- รัน `git diff HEAD~1 -- server.js` ดูว่า backend เปลี่ยนแค่ไหน และลองถอดกลับด้วยมือเพื่อเห็นว่าด่านข้อ summary พังกลับทันที
