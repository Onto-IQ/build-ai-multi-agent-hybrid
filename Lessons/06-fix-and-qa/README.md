# Module 06 — มีคนตรวจ แล้วปิดด่าน 6/6

## Key idea / แนวคิดหลัก — เล่าเป็นเรื่อง

"เสร็จแล้วครับ" จากปากผู้ช่วยไม่ใช่หลักฐาน โมดูลนี้แยกคนสองหน้าที่ออกจากกันในเครื่องมือเดียว: รอบแรกให้ `qa` (agent อ่านอย่างเดียว) ยิงแอปตามสคริปต์ด่านแล้วเขียนรายงาน — ห้ามแก้โค้ด รอบสองค่อยสั่งแก้ **ตามรายงานเท่านั้น** ผลที่ได้คือทุกบรรทัดที่ถูกแก้มีที่มาจากรายงาน จบด้วยการรันด่านต่อหน้า: **6/6 ผ่าน exit 0** โดยตัวตรวจ (`scripts/quality-gate.js`) ไม่ถูกแตะแม้บรรทัดเดียว

รายงานคือของที่ส่งมอบระหว่างสองหน้าที่ ถ้าไม่มีรายงาน จะไม่มีทางรู้ว่าแก้ครบหรือแก้เกิน วงจรเต็มปิดด้วยตา qa ตัวเดิม:

```text
gate แดง 4 เคส (จดก่อนแก้)
    → qa รีโปรดิวส์ + เขียน docs/QA-REPORT.md   (handoff 1)
    → แก้ตามรายงานเท่านั้น                     (handoff 2)
    → คุณรัน npm run gate → 6/6 exit 0
    → qa รันรีโปรดิวส์เดิมซ้ำ + append Evidence after fix   (ปิดวงจร)
```

และตอบข้อโต้แย้งที่ต้องเจอทุกปี — "ให้คนเป็น orchestrator ไม่ practical": ในงานจริงไม่มีใครพิมพ์แชทแทนเอเจนต์ทุกประโยค แต่ orchestrator ยังมีเสมอ ย้ายจากนิ้วคุณไปเป็น conductor prompt / skill / CI ที่วิ่ง**สัญญาเดิม** สิ่งที่ไม่ practical คือไม่มีสัญญา ไม่ใช่มีคนกดทีละขั้น รอบ A ในแล็บนี้คือรอบเรียนรู้ให้เห็นสัญญา รอบ B (ใน LAB) encode สัญญาเดิมให้เครื่องวิ่งซ้ำพร้อมจุดหยุดให้คนปิดด้วย gate

## Concept / เนื้อหา

### Part A — สองรอบสองบทบาท (จากเครื่องทดสอบจริง)

| รอบ | บทบาท | ของที่ได้ |
|---|---|---|
| 1. ตรวจ | เรียก `@qa` (`.claude/agents/qa.md` — tools มี Bash ให้ยิง request ได้ แต่ห้ามแก้โค้ด) | `docs/QA-REPORT.md`: ยิง `npm run gate` เองได้ exit 2, ตารางรายเคส, สามจุดพังอ้าง `server.js:บรรทัด` พร้อมวิธีรีโปรดิวส์, ปิดค่า `sk-***` ตามกฎ |
| 2. แก้ | เรียก `@developer` (เอเจนต์จาก Module 05) สั่งแก้ "เฉพาะจุดในรายงาน" | `server.js` +45/−10: JSON เพี้ยน→400 `INVALID_JSON` ไม่ล่ม, text ว่าง→400 `INVALID_TEXT`, โน้ต→201 + เขียน `data/notes.json` + GET `/api/notes`, health ตอบ `{ ok: true }` → **6/6 exit 0** |

จุดที่ต้องเข้มที่สุดคือ `notes-persists`: ด่าน kill เซิร์ฟเวอร์จริงแล้วบูตใหม่ โน้ตต้องอยู่ (survives-restart=yes) — ทางลัดเก็บในหน่วยความจำโดนจับทันที

### Part B — ขอบเขตที่วัดได้

การแก้ที่ถูกต้องมีสองข้อจำกัดวัดจากด่าน: (1) `scripts/quality-gate.js` diff ว่าง (2) ยอดสรุปยังตรง 16,772 / 45,341,868,784 ถ้าข้อไหนเพี้ยนแปลว่าแก้เกินขอบเขต แม้ด่านจะยังเขียว

## ลำดับในห้อง (ภาพรวม)

0. รัน `npm run gate` จด FAIL ทั้งสี่ก่อนแก้ — อย่าแก้ก่อนมีรายงาน
1. สร้าง `qa` + ให้เขียน `docs/QA-REPORT.md` → เปิดด้วยตา ต้องมีสามจุดพร้อมอ้างบรรทัด
2. ปิดเปิด claude ใหม่ → สั่งแก้ตามรายงาน → ให้มันรัน gate เองแล้วรายงาน exit code
3. รัน `npm run gate` ต่อหน้าเอง → `6/6 passed` + exit 0
4. โพสต์โน้ต รีสตาร์ทเซิร์ฟเวอร์ โน้ตยังอยู่
5. รอบปิดวงจร: สั่ง qa append `Evidence after fix` ลงรายงานเดิม
6. (ต่อยอด) รอบ B conductor prompt ใน LAB — encode สัญญาเดิมให้เครื่องวิ่ง

แบบฝึกหัดเต็มอยู่ที่ [LAB.md](LAB.md) ประมาณ 50 นาที

## Common pitfalls / กับดัก (จากเครื่องทดสอบจริง)

- **ไฟล์ `nul` ตกค้างที่รากโปรเจกต์** — จากคำสั่ง `... > nul` สไตล์ cmd ที่ผู้ช่วยรันใน Git Bash `git add -A` จะพัง ("short read while indexing nul") ลบทิ้งก่อน commit
- **สลับเครื่องมือโดยยังไม่ปิดตัวเก่า** — พิมพ์ `claude` ตอน opencode ยังเปิด คำสั่งกลายเป็นข้อความใน session เก่า เสียทั้งรอบ ปิดด้วย `/exit` ให้เห็นพรอมต์ PowerShell ก่อนพิมพ์คำสั่งถัดไป
- **ให้ qa กับคนแก้เป็นคำสั่งเดียว** — รายงานจะหาย กลายเป็นแก้แบบไม่มีหลักฐานว่าครบ
- **รอบแก้ไปแตะยอดสรุป** — จำกัดขอบเขตด้วยคำสั่น "อย่าทำยอดสรุปให้เพี้ยนจาก Module 05" และตรวจซ้ำด้วยตัวเลขหลังจบ

## Quick check / ทบทวน

- ทำไมรอบตรวจต้องห้ามแก้โค้ด? — เพื่อให้รายงานเป็นอิสระจากคนแก้ และวัดได้ว่าแก้ตามของที่ตรวจเจอ ไม่ใช่ตามที่คนแก้คิดเอง
- รู้ได้ยังไงว่าแก้เกินขอบเขต? — `git diff -- scripts/quality-gate.js` ต้องว่าง และตัวเลขยอดสรุปต้องตรงเดิมเป๊ะ
- โน้ตต้องผ่านยังไงถึงนับว่าทน? — เขียนลง `data/notes.json` ตอนรับ POST แล้วด่าน kill + บูตใหม่ยังอ่านเจอ

## Go deeper

- อ่าน `docs/QA-REPORT.md` เทียบกับ `git diff HEAD~1 -- server.js` ทีละจุด — ทุกจุดแก้ต้องมีที่มาในรายงาน
- ลองโพสต์โน้ต รีสตาร์ท แล้วดู `data/notes.json` ด้วยตา
- ถาม claude ว่าถ้าต้องรองรับผู้ใช้พร้อมกันหลายคน การเขียนไฟล์ตรง ๆ มีความเสี่ยงอะไร (ปูทาง Module 13 เรื่อง Vercel อ่านอย่างเดียว)
